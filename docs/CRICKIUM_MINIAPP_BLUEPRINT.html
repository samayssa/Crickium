01 / Product overview

Crickium's Mini App is a signed, authenticated web surface for managing the parts of the game the repository already persists. It complements the Telegram bot instead of replacing its commands or match engines.

Product goal

Make a player's club status, cards, live/open matches and rewards easy to inspect from a polished mobile interface.

Design principle

Show the actual database value, clearly mark unknowns, and route mutating actions through server-side validation.

Audience

Crickium Telegram players on iOS and Android, with a responsive browser layout for development.

Architecture

Static HTML/CSS/JS served by the Python ASGI backend, authenticated with Telegram Mini App initData.

Baseline rule: this implementation uses the latest uploaded Crickium repository as its source. It does not merge earlier ZIPs or recreate an unrelated game service.

Repository inspection findings

The project already contains a PostgreSQL data layer, player catalogs (global, special editions and showcases), JSON squad ownership, user currency/progression, match engine setup/state, quest assignments/completions and daily reward records. A Mini App service existed but the previous interface was a demo-style lobby, the root HTML route incorrectly depended on auth before initData could be sent, and its direct player queries were not using the bot's shared connection lifecycle. Those integration gaps were addressed without rewriting the match engines. The source ZIP contained hard-coded private credentials, so the delivered configuration reads those settings from `.env`/host environment instead of retaining the embedded values.

Main user journeys

  1. Check in: open Home → verify level, XP, coins, rubies, current rank, squad count, recent records, open matches, daily streak.
  2. Scout: type a player name → results update while typing → select a card → inspect available batting/bowling performance rows.
  3. Buy: open Market → filter role / country / OVR / price → confirm displayed coin cost → server validates ownership, balance and squad capacity → card is added to the caller's own squad.
  4. Claim: open Rewards → check server eligibility → claim the current daily reward or hourly Kit Bag → backend writes wallet/card and claim time.
  5. Review: Matches shows actual active setup/quest summaries and refreshes while open; Rank uses stored level/XP with match aggregates.
The app intentionally does not introduce squad editing or in-app trade/sell actions because those authoritative operations are not exposed by the uploaded backend.

Daily quest preview on Home and a dedicated daily/weekly/monthly board backed by the existing quest engine. It reports assigned tasks, completion state, and actual configured reward values.

Security controls

  • Telegram HMAC signature verification with constant-time compare.
  • Reject duplicate initData keys and invalid/future/older-than-six-hour auth dates.
  • Ignore client-asserted account IDs; viewer is parsed from signed Telegram user JSON.
  • Separate opt-in `MINIAPP_DEBUG_AUTH`, disabled unless explicitly enabled.
  • Per-user GET/POST request throttles.
  • Request JSON size cap, method allowlist, static path traversal check.
  • Balance, ownership, squad cap and reward cooldown checked on the server.
  • Database transactions serialize same-account purchases and claims.
Deployment secret rule: provide the existing bot token and database URL from environment/host secrets. This package documentation never prints secret values. Set `MINIAPP_DEBUG_AUTH` off in production.

Market filter implementation

Queries the real card sources with a bounded catalog window, calculates buy prices via the repo's current OVR chart, applies role/country/overall/bat/bowl/price filters, then sorts by the selected field. A truncation notice appears if the bounded scan reaches its cap, and users can narrow by name.

Kit Bag rule

Eligibility is computed on the server. The app chooses a non-owned global player whose real stored OVR equals 85, checks 25-card capacity, inserts that player into the signed-in user's squad and stores the claim timestamp atomically. If the exact rating is absent or all candidates are owned, the claim safely fails rather than fabricating a player.

Known data gaps

  • Most engine tables persist setup/status but not completed scorecards. Quest match summary rows are per user, not a universal public match ledger.
  • player_user_match_stats is scoped to the authenticated player and does not record fours/sixes. Highest runs and best wickets are maxima of that player's recorded match rows, not guaranteed career records.
  • Coin/ruby movements are not all written to a unified transaction table; wallet history therefore shows recorded quest reward credits only.
  • No separate achievement-unlock table was found; current assigned quests are exposed instead.

06 / Cloudflare & deployment

The ZIP includes the genuine Cloudflare Tunnel release for Linux x86-64. The binary was downloaded from Cloudflare's official release page, SHA-256 checked against the official release API digest, marked executable and version-checked.

Local smoke run

  1. Install packages: python -m pip install -r miniapp_backend/requirements.txt.
  2. Set DATABASE_URL and BOT_TOKEN through a private secret manager.
  3. Start python launcher.py. The backend listens on localhost:8000 by default, and cloudflared creates a temporary public HTTPS URL.
  4. Configure that URL in the bot's Mini App settings or `MINIAPP_URL`; use a named tunnel for production stability.
  5. Open from Telegram and test the real signed user flow; never deploy with `MINIAPP_DEBUG_AUTH=1`.
Do not ship tunnel credentials. The bundled binary is an executable, not an account credential. Quick tunnels need no local secret, but a stable named tunnel must use credentials stored outside this repository.

Production checklist

  • HTTPS origin set in Telegram.
  • Debug auth disabled.
  • Secrets supplied by host runtime.
  • Database migration completed and backup verified.
  • Check logs, DB quotas, request limits.
  • Use fixed domain and named tunnel / managed ingress.
  • Test from a Telegram account with real initData.
  • Validate purchase and claim effects in DB before public rollout.

Recommended staged release

  1. Deploy to a staging database; verify additive migration and read-only screens.
  2. Exercise all purchase and claim boundary cases using a disposable Telegram test account.
  3. Check squad JSON, balances, quest events and cooldown timestamps after each mutation.
  4. Deploy behind the existing Telegram Mini App entry point and watch database usage/errors.
  5. Only then consider extra bot schema for full scorecards, achievements and ledger history.
This blueprint describes the repository and implementation, not a claim of live production execution. Verify data-dependent mutation flows against staging before launch.
